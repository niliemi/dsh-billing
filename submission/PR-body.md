# Add niliemi/dsh-billing (usage)

Single-entry submission: adds `data/plugins/niliemi__dsh-billing.yml`. Nothing else in this repo is touched.

## What it is

`yoka-dsh-billing` is a DSH plugin that prices token usage and lets you cap it.

- The host half folds a session's token usage into a local ledger (uncached input / output / cache read / cache write, kept per turn+step, replacements not re-additions), multiplies each bucket by the official `@earendil-works/pi-ai` price table (`lib/pricing.json`, generated by `tools/build-pricing.mjs`: 32 providers / 605 models, USD per million tokens), applies an editable rate, and serves the result over local `/plugin-billing/*` HTTP routes.
- The browser half registers two entries in the `conversation.composer.dock` slot, so `● ¥0.0834 / ¥50.00` (this session) and `● ¥12.3600 / ¥1000.00` (global) sit on the same row as the composer's context meter, each with a green / amber / red dot. It also registers one entry in `sidebar.footer.action`, showing `余额 ¥1007.20` beside the Settings button at the sidebar foot.
- The global ceiling is **set by you** in the panel (empty = no ceiling, never blocks). Your DeepSeek account balance (top-up **plus** bonus, read through the host `deepseekAccount` service, refreshed every 60 s) is only the boundary and the reference: a ceiling above it is clamped down to it (`ceilingSource: "limit-clamped"`), and when the balance is unavailable or zero nothing is clamped, so your own number stays in force. Per-session ceilings are set per session and are entirely independent of one another — there is no shared default (0.2.2 removed the one that used to apply to every session), never clamped, and empty / 0 means that session has no ceiling. When spend reaches a ceiling, the host returns `{ kind: "reject" }` from the `agent/pre-step` waterfall, so that turn ends without sending an LLM request — after a confirmation dialog offering a one-off override, a session-only override, top-up, or raising the ceiling.
- Clicking either chip (or the sidebar balance) opens the panel: account balance breakdown, the editable global ceiling, per-session ceiling inputs (one per session, independent), rate, guard switch, per-model price overrides and per-session breakdown. There is no "already topped up" field — that was a 0.1 leftover and the ceiling no longer equals the balance.

Values are stored as tokens plus the model key, never as money: changing the rate or a model price re-prices all history immediately.

## Why `usage`

It reports and limits cost/consumption. It does not render conversation, choose models, or add tools.

## Manifest facts the CI checks

- `package.json` declares **`dsh.bundle`** (`cordis.patch.yml`) and `dsh.client` (`platform: "web"`, `exports["./client"]`).
- No `@deepseek-ai/*` runtime dependency: the host half uses only Node built-ins, the browser half only `require("react")` and `require("react-dom")` from the frozen platform modules. Its only host service is an **optional** `ctx.get("deepseekAccount")` (balance), which degrades to "no clamping, self-set ceiling still applies" when absent. So there is no peer range that could silently exclude a prerelease host.
- `files` ships exactly `lib/index.js`, `lib/client.js`, `lib/pricing.json`, `cordis.patch.yml`, `README.md`. The browser bundle needs no build step (hand-written `window.__ModuleLoader__.load` factory).
- Repository has real, working code (not a package that only lists dependencies) and will carry the `dsh-plugin` topic.

## How it was verified

- `node tools/self-test.mjs` → 107 passed / 0 failed (pricing, replacement folding, rate re-pricing, balance = top-up + bonus, a self-set global ceiling that is clamped to the balance, an unset ceiling never blocking, balance-unavailable leaving the self-set ceiling in force, global and per-session ceilings, per-session ceilings that are independent of each other and of the removed legacy default, over-limit reject with `blockScope`, one-off / session-only overrides, request guard, persistence, route teardown, 0.1 ledger migration written back to disk with the legacy shared default carried onto each session).
- `node tools/self-test-client.mjs` → 80 passed / 0 failed (module shell, slot registrations, both chips, unset-ceiling wording, sidebar balance, panel fields including the editable global ceiling and neither "top-up amount" nor "per-session default ceiling", two sessions rendering one independent ceiling input each, both confirm dialogs, overlay toggling, effect cleanup).
- Installed into a live DSH profile: `GET /plugin-billing/state` returns 200 with real usage, the client slot tree shows the `billing` entry active in `conversation.composer.dock` next to the shipped meter, and the `billing-balance` entry active in `sidebar.footer.action`.

## Closest existing entries (checked before opening this)

`usage` already lists 235 entries. Three overlap with parts of this one, so here is the honest delta rather than a claim of novelty:

- **PerryLink/dsh-budget** — four-bucket token metering, USD pricing from a built-in table with overrides, session/daily/monthly caps, and over-limit policies including `block`. This is the mature implementation of the same core idea. Its own README lists its surfaces as the Settings budget tab plus the `/budget` command.
- **02Muller25/dsh-api-balance** — account balance readout. We overlap in part here too: version 0.2 shows the balance at the sidebar foot (top-up + bonus, refreshed every 60 s), and that balance is the boundary the self-set global ceiling is clamped to. It is still not a separate readout: the same number is what stops a turn when your ceiling overshoots it.
- **songoao25/dsh-bottom-info-bar** — a bottom info line with provider/model, balance, peak pricing and per-session spend.

What this submission actually adds: resident chips inside `conversation.composer.dock` — the row that already carries the shipped context meter — rendering `<symbol><spent> / <ceiling>` for **this session and globally** side by side (e.g. `● ¥0.0834 / ¥50.00` and `● ¥12.3600 / ¥1000.00`), with a **user-set global ceiling** (clamped to the account balance, which is read from the host `deepseekAccount` service as top-up + bonus), a per-session default plus per-session overrides, an editable CNY rate, and a confirmation dialog before the block (one-off / session-only / top-up / raise the ceiling). It is deliberately **not** a budget engine: no daily/monthly windows, no carbon or latency accounting, no audit events, no per-plugin budgets.

If the maintainer judges this a duplicate of `dsh-budget`, I would rather be told than have the list carry the same thing twice — closing or narrowing the entry is fine.
